## 问题列表

### [major] 被拒绝的分解请求仍会晋升待人工审核的任务

位置：`hermes_cli/kanban_storage_catalog.py:293–296`

关联位置：

- `hermes_db/domains/kanban/postgres/catalog.py:557–561`
- `hermes_cli/kanban_db_graph.py:129–133`
- `tests/hermes_db/postgresql/test_kanban_tasks.py:121–126`

**问题：** `decompose_task_rows()` 对不存在、非 `triage` 或已经分解的根任务返回 `None`。抽取后的应用函数没有保留原来的提前返回，随后仍按默认 `auto_promote=True` 调用 `recompute_ready()`。

基准实现在上述拒绝条件下直接返回，跳过晋升；SQLite sibling 也保留这一行为。`recompute_ready()` 会遍历当前 Board 的 `todo`、`blocked` 任务，更新满足条件的任务状态并写入 `promoted` 事件，因此这不是额外的只读检查。

**具体触发场景：**

1. 首次执行有效分解，指定 `auto_promote=False`，使子任务保留在 `todo`，等待人工审核。
2. 再次对同一已分解根任务调用分解，采用默认 `auto_promote=True`。
3. 本次调用虽然返回 `None`，却会把满足条件的子任务晋升为 `ready`；也可能影响同 Board 的其他任务。

**影响：** 被拒绝的操作产生跨任务状态修改，破坏原有“人工审核后再晋升”的正常流程，并使 PostgreSQL 与 SQLite 行为不一致。该变化违反本次仅调整职责归属、保持业务算法的要求。

**建议：** 在取得 `ids` 后，若 `ids is None`，立即返回。仅成功分解后执行自动晋升。

补充一个行为合同：首次使用 `auto_promote=False` 分解，再次分解被拒绝后，断言子任务仍为 `todo`，且未新增晋升事件。现有测试仅断言重复调用返回 `None`，无法捕获此副作用。上述问题由代码控制流静态确定；Reviewer 未执行动态复现。

未发现其他已确认的 blocking、major 或 minor 问题。
