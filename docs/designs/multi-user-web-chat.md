# Hermes 多租户 Web 服务与弹性工作池设计草案

## 文档状态

- 状态：NEEDS_USER_DECISION
- 创建日期：2026-11-05；最近更新：2026-11-06
- 当前阶段：完整会话 PostgreSQL 接入的设计和实施计划已准备，按新库实施、不迁移旧数据；配置和用户 Markdown 后续收敛。数据库实例由用户管理，尚未开始运行代码改造或集群验证。
- 当前约束：共享多用户 Web 服务，容器化或 Kubernetes 部署，按负载扩缩容；用户明确不接受每用户一套常驻 Hermes。

## 背景与目标

面向外部用户提供类似 ChatGPT 的网页对话入口，用户各自拥有独立数据和会话，保留绝大部分 Hermes 能力，接近本地安装。共享服务实例通过任务调度复用，任意代码执行通过按需租约隔离。注册用户数不决定 Hermes 常驻实例数。

推荐拆分 Web API、Agent Worker、隔离执行池和共享持久化。Web 接入及 Agent 工作池可随负载扩缩容；代码、终端、浏览器和不可信扩展获得任务或活跃会话级沙箱。长期用户数据与临时计算资源分别管理。

当前先推进数据层收敛设计：明确对话、配置、提示词、记忆、技能和文件的权威来源、归属、版本及读写入口，再实施多副本和任务池验证。文件格式本身不决定是否适合 Web 部署。

## 已确认范围

- 外部用户登录网站，拥有私有会话、记忆、文件、Skills、工具配置及凭据。
- 保留工具执行、终端、代码、文件、MCP、插件、浏览器、子 Agent 及定时任务。
- 共享 Web 服务和任务工作池，可容器化部署并横向扩缩容。
- 不给每位注册用户分配固定常驻 Hermes 进程或 Pod。
- 用户本机的文件、桌面和硬件不自动成为云端执行资源；相关连接另行授权。

## 功能与非功能要求

用户可以聊天、上传下载文件、继续历史、停止执行、处理审批、使用云端工作区及兼容的扩展。前端可复用现有 Webapp 的组件与交互，但不能继续假定一个后端代表一个本机操作者。

所有 API、队列消息、事件订阅、文件、工具、记忆和密钥访问必须绑定可信用户及租户上下文。状态不能仅依赖 Web Pod 内存或临时磁盘。缩容和故障恢复必须保留幂等、会话写入顺序、审批代次及未知执行结果语义。

当前不设计支付结算、组织协作、公开分享和本地硬件连接。数据库、队列、沙箱技术及目标容量在原型验证后确定，不预先承诺未测量的吞吐或费用。

## 现有实现与主要改造点

- SECURITY.md：当前 Hermes 是单租户个人 Agent。允许任意代码和插件时，应用层 Profile 分隔不能替代执行隔离。
- gateway/session_authority.py：已有持久准入、顺序执行、执行代次和恢复逻辑；LiveSession 的订阅、锁、审批和活动任务仍有进程内状态。
- agent/turn_facade_lease.py：已有会话 turn lease 和失租中断，迁移到分布式存储时必须保持这些语义；不能只增加一把普通缓存锁。
- hermes_state.py：SessionDB 使用本地 SQLite 和 WAL。多个 Pod 共享同一目录不等于获得经过验证的分布式状态后端，需明确存储接口和迁移方案。
- gateway/run_agent_cache.py：AIAgent、工具连接、停止控制及会话缓存包含本地所有权，不能让负载均衡器随机选择当前执行者。
- gateway/platforms/api_server_memory_sessions.py：记忆管理器在请求间保留实例及预取状态。跨 Worker 恢复需处理其提供商契约，不能只恢复聊天正文。
- tools/code_execution_tool.py、tools/code_kernel.py、tools/code_kernel_remote.py：存在会话级持久解释器及远端执行路径，可复用执行后端，但 Python 变量、Shell 和浏览器进程不能当作普通数据库记录自动迁移。
- plugins/AGENTS.md、SECURITY.md：Python 插件会加载进 Agent 进程。用户自装插件不能直接导入多租户共享 Worker；需要隔离插件执行协议，或为该运行租用完整隔离 Worker。
- hermes_cli/web_host_terminal.py：现有网页终端打开网关环境的 Shell。产品终端需路由到获授权的沙箱会话，不能打开 API 或共享 Worker 的 Shell。
- cron/AGENTS.md：当前调度有 per-home tick lock、本机所有权和进程内在途状态。集群部署需统一的触发准入与执行租约，防止每个副本重复调度。
- agent/AGENTS.md：会话的系统提示词、工具定义和既有上下文需保持稳定。Worker 迁移应恢复固定快照，不能从最新磁盘配置重建过去的提示前缀。

## 方案比较

### A 共享服务与 Agent Worker 加独立执行池

Web API 完成认证、授权、准入和订阅；持久队列调度 Agent Worker；Worker 执行可信的对话编排，调用沙箱执行终端、代码、浏览器和扩展。不可信用户代码不进入共享服务进程。

平台提供的可信插件可随 Worker 镜像部署；用户扩展需要在执行池中提供等价的工具、配置及生命周期适配。对必须依赖 Agent 进程内 Python 状态的扩展，使用任务级完整隔离 Worker 兼容通道；租约与资源按活跃运行分配，不固定绑定注册用户。

### B 按活跃会话租用完整隔离 Hermes Worker

共享 API 及调度不变，运行时从池中租用完整隔离 Hermes，装载用户状态，完成后释放。保留当前进程内插件语义的成本较低，但状态装载、依赖缓存和冷启动成本较高；有终端、浏览器、解释器及后台进程时，租约需要持续到活动上下文结束。

该方案按并发活动分配资源，也不要求每用户常驻实例。可作为 A 中复杂扩展的兼容实现或原型对照。

### C 原样部署多个 Hermes 副本共用目录

直接为现有 Webapp 或 gateway 配置多个 Deployment 副本，再共享用户目录并交给 HPA。改动表面较少，但会话所有权、SQLite、内存状态、定时触发和插件权限仍未解决，不适合作为本产品的架构。

| 维度 | A 共享编排与执行池 | B 按需完整 Worker 池 | C 原样增加副本 |
| --- | --- | --- | --- |
| 实现复杂度 | 高，需服务化和执行边界改造 | 中到高，需租约及状态装载 | 表面低，正确性风险高 |
| 能力兼容 | 需适配进程内扩展及实时状态 | 最接近现有单运行时语义 | 无法保证多用户正确性 |
| 维护成本 | 维护状态、执行及协议契约 | 维护镜像、依赖和池调度 | 持续处理竞态与数据问题 |
| 扩容单位 | API 请求、Agent 运行、沙箱租约 | 活跃会话或兼容任务 | 整个 gateway 副本 |
| 资源利用 | 可按不同工作负载独立调节 | 无固定用户常驻成本，有活跃租约成本 | 无有效跨副本资源模型 |
| 测试重点 | 多租户、恢复、事件及工具边界 | 隔离、装载、清理及恢复 | 缺少基础语义无法验收 |

## 推荐方案

采用 A 作为目标架构，并以 B 处理确实要求进程内完整兼容的扩展。共享工作池服务不同用户任务，但不让两个不可信用户在同一个可任意执行代码的上下文内共享权限。

不再采用每用户固定常驻环境。用户数据持久化到共享存储中的受控租户命名空间；Worker 和沙箱容量由活跃执行需求决定。预热镜像和可复用基础资源降低启动成本，跨租户复用前必须销毁旧执行上下文并清理凭据及可写层。

这是对 Hermes 的服务化、多租户和分布式状态改造，不能通过增加一份 Kubernetes YAML 完成。产品平台和执行服务优先放在独立项目或现有边缘扩展中；必要的核心改造需围绕具体存储及执行契约评估，避免将产品账号和计费逻辑塞入 Agent 核心。

## 服务职责和数据流

1. 浏览器登录后，Web API 从可信登录态解析用户及租户，验证目标会话归属、额度和请求标识。
2. 在共享事务存储中提交准入记录和可靠派发意图，再投递持久任务队列。消息重复投递不能产生重复运行。
3. Agent Worker 领取运行租约和会话所有权，装载固定的提示词、模型、工具、记忆和配置快照。同一会话串行写入，不同会话可并发。
4. 工具请求携带受控执行上下文，通过执行服务获得沙箱租约。仅挂载相应用户授权的数据，凭据按任务提供。
5. 内容及运行状态写入可恢复事件记录，再向浏览器推送。重连可到任意 API 副本，根据事件序号续读。
6. 停止、澄清和审批经授权后发送到当前运行的 Worker，并验证执行代次；旧 Worker 的结果不能覆盖新所有者。
7. 工作区文件在明确的同步点或持久卷上保存。普通完成可释放沙箱；活动终端、浏览器、解释器和后台任务持有更长租约。
8. 定时任务由独立调度职责产生持久运行，不依赖某个 Web Pod 常驻。领导选举或集群原子准入确保一个应触发时刻不会并发提交多份。

## 状态与数据结构

共享事务数据库作为用户、会话、运行、审批及执行所有权的权威来源；对象存储保存附件、文件快照及大结果；低延迟缓存用于路由和可重建信息。具体产品选型待定，缓存失效不能破坏租约代次和持久准入。

| 实体 | 关键字段及约束 |
| --- | --- |
| Tenant / User | 可信身份、状态和额度；前端提交的 user_id 不能替代登录主体 |
| Conversation | 租户、用户、会话 id、固定配置快照、转录版本；所有访问验证归属 |
| Run / Admission | 请求标识、会话、输入版本、状态、派发记录；同请求只准入一次 |
| RunLease | 持有者、到期时间、单调代次；提交结果、文件写入及控制动作需要验证所有权 |
| Event | 会话、运行、序号、类型及终态；重连恢复不能重复创建运行 |
| Approval | 运行、请求 id、执行代次及选择；过期或跨用户请求拒绝 |
| SandboxLease | 所属主体、运行或会话、环境引用、代次、状态、资源限额、过期时间 |
| Workspace | 归属、持久数据引用、版本和写入租约；保护跨沙箱并发修改 |
| JobDefinition / Occurrence | 所属主体、时区、计划及触发时刻；触发准入保持唯一 |

已有 SQLite 和文件型配置如何迁移到集群存储，需要单独设计兼容边界。首个原型不导入现有个人 Profile；外部记忆服务仍需校验实际 scope，不能把不同用户共享一个记忆提供商实例当成隔离。

## 候选接口与上下文

产品 API 提供当前用户会话、消息提交、运行查询、事件恢复、停止、审批、文件和沙箱终端。浏览器使用产品资源标识，不能指定任意上游地址或切换其他租户的 Profile。

内部任务至少携带 tenant_id、user_id、conversation_id、run_id、execution_generation、config_snapshot_ref 和受限凭据引用。执行请求另含 sandbox_lease 与允许的挂载、网络和资源策略。内部调用也要认证，不能只依赖网络地址。

前端继续复用 Webapp 组件；原生网关协议需通过平台适配，覆盖流式回复、审批、文件、插件、终端和浏览器，不假定 Chat Completions 接口足够提供全部功能。

## 插件和近似本地体验

平台信任的扩展可在发布时安装到 Worker 镜像。用户安装的第三方 Python 插件、Hooks 和 MCP 放到隔离执行环境；如果其机制要求读取或修改整个 Agent 进程，租用完整隔离 Worker 或实现明确的远端扩展协议，不能在共享 Worker 中直接导入。

用户安装的依赖及可写文件可以持久化；活的进程状态另行管理。数据库中的聊天历史不能自动恢复 Python 内存变量、Shell 前台进程或浏览器登录进程。需要持续状态的功能保留租约和亲和路由；宿主故障后明确说明哪些状态可恢复，哪些执行结果未知。

活跃独立终端、浏览器或任意代码上下文仍需要相应隔离资源。工作池降低闲置常驻成本，不意味着所有同时运行的用户可安全共用一个 Shell 或 Python 内核。

## Kubernetes 扩缩容

- API Deployment 可按请求量、连接数、延迟和资源指标扩缩容；浏览器连接与事件源解耦后可重连其他副本。
- Agent Worker 工作池按待执行队列、等待时间、在途运行和可用执行槽扩缩容。模型等待通常不消耗很多 CPU，不能只用 CPU 判断容量。
- 执行池按活跃沙箱、等待租约、CPU、内存及浏览器资源需求扩缩容；连接空闲与执行空闲分别判断。
- HPA 支持资源、自定义和外部指标；KEDA 可按事件或队列指标驱动工作负载扩缩容。具体适配器、阈值及最小预热容量需负载验证。
- 缩容先停止领取新任务并进入 draining，再完成活动运行或到达明确的可恢复边界。宽限期到达后进程仍可能被强制终止，不能承诺任意运行透明迁移。
- 故障恢复依赖持久记录和过期租约。任务队列通常可能重复派发，外部副作用还需操作幂等或未知执行结果处理，不能宣称端到端绝对只执行一次。
- 不对同一个 Deployment 配置互相竞争的 HPA 控制器。KEDA 与 HPA 的关系、长任务缩容策略需要按选定版本验证。

参考：[Kubernetes HPA](https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale/)、[KEDA 工作负载扩缩容](https://keda.sh/docs/2.21/concepts/scaling-deployments/)、[Pod 终止流程](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)。

## 错误、迁移及回滚

区分未准入、已排队、运行中、等待审批、完成、失败、取消及执行结果未知。网络断开、租约过期或 Worker 死亡不自动授权重新执行有副作用的工作。审计关联用户、会话、运行、执行代次和沙箱，不记录平台密钥。

先用隔离的测试用户及存储构建双副本原型，验证外部状态和任务租约；不直接将个人数据目录挂给多个 Pod。正式接入存量数据前设计导入和一致性校验。回滚保留可恢复的事务数据、文件版本和快照，不假定旧程序能读取已迁移模式。

## 风险与验收

| 风险 | 验证要求 |
| --- | --- |
| 跨用户会话、记忆或文件访问 | 两个真实用户并发运行，交叉猜测资源标识、审批及订阅均被拒绝 |
| 两个 Worker 同时写同一会话 | 租约过期、网络延迟及旧 Worker 恢复后，旧代次不能提交结果 |
| 重复消息或定时触发重复执行 | 重复派发、重试和副本切换保持稳定准入，未知结果不自动重跑 |
| 缩容丢失回复、审批或任务 | 活动运行 drain；强制删除时有持久状态与明确恢复语义 |
| 任意插件读到其他租户或平台凭据 | 插件、MCP、代码和终端隔离测试覆盖进程、文件、网络和秘密 |
| 沙箱复用残留数据 | 跨租户复用前旧凭据、可写层、进程和浏览器状态均不可见 |
| 配置重建破坏提示缓存 | Worker 切换后系统提示、工具集和历史前缀与会话快照一致 |
| 同步文件覆盖和进程状态丢失 | 双会话工作区写入冲突可判定；终端和解释器的恢复范围明确 |

至少验证两个 API 副本、多个任务 Worker、两个租户、多次重复派发、一个活动运行中的 Worker 故障和一次受控缩容。具体容量与恢复时间目标在资源和并发要求明确后制定。

## 数据层收敛作为先行阶段

### 数据分类和权威来源

| 类别 | 当前主要形态 | Web 部署的目标 |
| --- | --- | --- |
| 会话和运行状态 | state.db、SessionDB、网关内存 | 通过会话存储契约访问共享事务存储，包含准入、转录、压缩、租约和执行代次 |
| 用户配置 | config.yaml | 复用 ConfigBackend，以可校验、可分层、可版本化的配置文档持久化；部署参数与用户可改设置分开 |
| 内置系统提示和默认模板 | 代码、仓库中的 Markdown 和资源 | 继续随代码或镜像版本发布，不为部署需要而全部搬入数据库 |
| 用户人格及自定义提示 | SOUL.md 等 | 按用户及 Agent 归属的版本化文本资源，保留 Markdown 内容和导入导出能力 |
| 工作区规则 | AGENTS.md 等项目文件 | 保留项目文件及目录优先级；会话记录所读工作区版本与有效内容 |
| 内置记忆及外部记忆 | MEMORY.md、USER.md、MemoryProvider | 归属明确的记忆存储，版本或并发控制；向量索引和检索缓存不替代正文权威来源 |
| Skills 和插件资源 | SKILL.md、脚本、模板、依赖、插件目录 | 元数据及启用关系受控保存，内容以带版本或摘要的完整资源包管理，执行时装载到沙箱 |
| 附件和生成产物 | 用户目录中的文件 | 元数据及归属进数据库，内容进入对象存储或受控文件服务，下载和删除遵守同一权限 |
| 可执行工作区 | 本地目录、Git 仓库、依赖目录 | 持久卷或版本化文件同步加沙箱中的真实目录，明确并发写入、冲突和恢复语义 |
| API key 和 OAuth 凭据 | .env、auth.json、秘密来源 | 密钥系统或加密存储加引用，按用户及运行授权；不得混进普通配置、提示词和日志 |
| 缓存及临时运行数据 | 缓存目录、PID、socket、解释器状态 | 可重建的本地临时数据或有独立租约的活动进程，不承诺全部可从数据库恢复 |

### 已有入口与新增边界

配置已有 hermes_cli/config_backend.py 的 ConfigBackend；远程后端位于 plugins/config_backends/remote/，支持版本、并发写入保护、配置层级和锁定键。这是已有可复用能力，不应新建第二套配置读写链路。但该后端面向 Agent 实例及 Profile，不等同于已实现 SaaS 用户授权；是否复用官方配置服务或实现自有适配尚未决定。

SessionDB 是现有会话门面，agent/runtime_session_store.py 提供受管 Worker 经会话所有者访问的现有契约。共享事务数据库适配必须保留准入、压缩、删除墓碑、执行代次和租约语义，并识别 SQLite 专有 SQL 和搜索功能；不能只把连接字符串改成另一种数据库。

agent/prompt_builder.py 的 load_soul_md 等路径仍直接读取 Markdown；tools/memory_tool_store.py 的 MemoryStore 管理内置记忆文件。根据具体调用链建立提示文本和内置记忆读写边界，复用外部 MemoryProvider 契约；不创建一个包揽所有资源的万能存储接口。

沙箱中的程序依赖真实文件系统。对象存储适合附件、资源包和快照，不能不经设计就替代支持 open、rename、锁、Git 和数据库文件的可写工作区。

### 归属与版本

数据库、文件服务及后台任务至少明确 tenant、user、agent、workspace、conversation 和 run 中适用的归属。所有标识从认证及授权记录解析，不能把客户端给的路径、Profile 名称或 HERMES_HOME 当成身份凭据。保留多 Agent 和多工作区关系，不把一个用户永久等同于一个 Profile。

本地模式继续使用已有路径解析；Web 模式中本地目录逐步承担缓存、导出和沙箱装载职责。不能通过每次请求修改全局 os.environ 来切换用户。线程、子任务和延迟回调都要携带已验证的资源上下文，避免落回服务启动账号的目录或配置。

配置和文本资源至少记录归属、资源类型、内容或对象引用、版本、摘要和更新时间。修改采用预期版本校验，拒绝覆盖更新；删除、回收、导入导出及备份也遵守相同归属。默认版本化、兼容导出和后台编辑必须保持单一权威来源，不长期双写本地文件与数据库。

### 提示词和配置快照

创建会话时固定影响系统提示与工具定义的配置、SOUL、内置记忆、有效项目规则和技能信息；记录必要版本引用，并保存能够重现实际组装结果的内容及顺序。仅记录版本名而无法取得旧内容，不足以恢复。

会话开始后修改用户人格或配置，默认影响后续新会话。已有会话继续使用固定的系统提示和工具前缀，显式更新按现有受控语义处理，不能因迁移 Worker 就重新加载最新文件。工具执行结果和新用户输入仍按正常消息流进入上下文。

内置记忆工具当前已在会话开始冻结 MEMORY.md 和 USER.md 快照，之后写盘不改变当前系统提示。这一契约迁移到远程存储时必须保持。秘密只通过引用及受限运行凭据提供，不将明文密钥写进提示快照。

### 建议收敛顺序

1. 建立数据清单：逐项标注归属、读写调用点、权威来源、缓存、锁、版本、备份及删除语义，确认 Web 所需最小访问契约。
2. 从已有 ConfigBackend 验证用户配置的远程读写与并发版本，继续提供本地 FileBackend；部署配置和秘密保持独立来源。
3. 收敛 SOUL、自定义提示和内置记忆的读写，加入版本及会话快照；项目 AGENTS 和完整 Skill 资源保留文件语义。
4. 设计会话存储适配，再接共享事务数据库；保持本地 SQLite 模式，覆盖完整会话与运行状态，不只搬 sessions 和 messages 两张表。
5. 收敛附件、产物及资源包；随后明确可执行工作区的挂载、同步和并发写入策略。任何本地缓存丢失后都能按授权重建。
6. 数据层能够独立恢复后，再验证多 API 副本、任务 Worker、沙箱租约和扩缩容。

以上为设计阶段的顺序，不是已批准的编码实施计划。每个阶段先交付可独立验证的读写链路，避免一次性重写整个用户目录。

### 数据阶段的验收

- 新建服务实例不依赖旧实例的本地用户目录，也能按身份取回用户的历史会话、配置、提示资源及已接入的附件。
- 用户 A 和 B 使用同名 Agent、同名 SOUL 及同名文件时，配置、正文、搜索、下载和后台操作仍不串数据。
- 编辑配置或提示产生新版本；两端并发保存不会静默覆盖，旧会话的提示前缀保持不变。
- 清空可重建缓存不造成数据丢失；恢复时不会自动改用默认用户配置或其他用户的数据。
- 本地安装仍可使用文件和 SQLite；切换后端有明确导入导出及回滚流程，不依靠长期双写。
- 对话存储后端替换保持压缩、重试、租约、删除和未知执行结果的现有行为；本轮用新数据验证，不包含 SQLite 旧数据导入。
- 活跃 Shell、浏览器和 Python 进程的迁移不计入数据阶段的恢复承诺，后续由执行租约设计解决。

## 重要决策与未决事项

已确认保留接近本地能力、服务外部用户，并采用共享服务及按负载扩缩容；已排除每用户常驻 Hermes。

当前优先项已进一步收敛：用户确认先做完整会话存储的 PostgreSQL 接入，覆盖消息、执行队列和租约；配置及用户 Markdown 留待后续。PostgreSQL 实例由用户管理，当前先核查数据访问结构、ORM 情况及连接配置入口。具体接入建议见 [PostgreSQL 会话存储设计](postgresql-session-storage.md)。

数据库层包统一命名为 `hermes_db`，内部划分表定义、数据仓储、业务事务、连接池与版本迁移；继续推荐 SQLAlchemy Core。目录和调用约定见 [数据库层代码组织设计](postgresql-storage-code-layout.md)。

用户进一步确认使用新 PG 库、不兼容或迁移旧数据。本轮实施范围已收敛，[会话后端实施计划](../plans/postgresql-session-storage-plan.md) 全部任务待执行；本文整体 Web/工作池架构的未决项不作为本轮数据库后端设计的阻塞。

仍需确认目标并发执行数、部署资源、可接受启动等待、长驻终端和后台任务保留策略、平台付费模型或用户自带凭据。完整进程内插件兼容通道和共享编排的边界需要原型验证。相关结果未确定前，状态保持 NEEDS_USER_DECISION，不宣称已具备生产级多租户能力。
